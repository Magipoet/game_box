# 记忆翻牌游戏 — 问题记录

## 问题 1：关卡信息布局过宽

### 现象
"第1关 (3×2)" 这行信息显示在关卡按钮的右侧，导致游戏界面整体过宽，布局不紧凑。

### 原因
关卡标签（`currentLevelLabel`）与关卡按钮（`levelBtn`）在同一行水平排列，关卡信息作为按钮的相邻元素显示在右侧，而非垂直排列在下方。

### 解决方案
将关卡信息区域用 `.level-info` 容器包裹，改为垂直布局（flex-direction: column），使关卡标签和星级显示位于关卡按钮的下方。同时添加响应式样式，在小屏幕上自动调整间距和字体大小。

**涉及文件**：`index.html`、`css/header.css`

---

## 问题 2：限时模式缺少暂停功能

### 现象
限时模式下没有暂停按键，玩家无法在中途暂停游戏；且游戏开始前不显示剩余时间，只有点击开始后才显示倒计时。

### 原因
原始实现中限时模式仅设计了一个计时器，没有考虑暂停需求；倒计时显示逻辑仅在游戏开始后（`startCountdown`）才渲染，游戏重置时未预先展示关卡时限。

### 解决方案
1. 在页面头部添加暂停按钮（仅在限时模式下显示）
2. 添加暂停模态框，显示当前步数和配对进度，提供"继续游戏"按钮
3. 修改 `resetStats()` 函数，在限时模式重置时立即显示该关卡的剩余时间
4. 新增 `pauseGame()`、`resumeGame()`、`hidePauseModal()` 函数，暂停时同时停止正计时和倒计时

**涉及文件**：`index.html`、`css/header.css`、`js/state.js`、`js/game.js`、`js/events.js`

## 问题 3：关卡标签中多余的计时信息

### 现象
- 常规模式下，关卡标签显示 `第1关 (3×2) ⏱️60秒`，其中的"⏱️60秒"在常规模式下是多余信息
- 限时模式下，关卡标签同样显示 `⏱️60秒`，但标题下方已有独立的倒计时显示区域，造成信息重复

### 原因
`updateDifficultyButtons()` 函数中通过 `modeText` 变量在限时模式下追加 `⏱️{timeLimit}秒` 文本，而该信息在两种模式下均属冗余——常规模式无需时间提示，限时模式已有专用倒计时区域。

### 解决方案
删除 `modeText` 变量及其在 `currentLevelLabel.textContent` 中的引用，关卡标签统一只显示 `第{N}关 ({cols}×{rows})` 格式。

**涉及文件**：`js/game.js`（`updateDifficultyButtons` 函数）

## 问题 4：常规模式与限时模式的星级和通关进度未分离

### 现象
常规模式通关某关卡后，切换到限时模式时，该关卡也被标记为已通关并获得了星级，两种模式的进度混为一体。

### 原因
星级数据仅使用单一的 `levelStars` 对象存储，`saveStars()` 和 `getTotalStars()` 函数不区分游戏模式，导致两种模式共享同一份星级记录。关卡解锁也仅使用单一的 `unlockedLevels` 对象，常规模式通关解锁的关卡自动在限时模式也可见。

### 解决方案
1. 新增 `timedLevelStars` 对象存储限时模式独立星级，新增 `STORAGE_KEYS.timedStars` 存储键
2. 新增 `unlockedTimedLevels` 对象存储限时模式独立解锁状态，新增 `STORAGE_KEYS.timedProgress` 存储键
3. 修改 `saveStars()` / `getStarsForLevel()` / `getTotalStars()` 函数，增加 `mode` 参数按模式分别存取
4. 新增 `unlockNextTimedLevel()` / `saveTimedProgress()` / `getUnlockedLevelsForMode()` 函数
5. 修改 `showWinModal()`，通关时根据当前模式分别保存星级和解锁下一关
6. 修改 `updateDifficultyButtons()` 和 `updateCurrentLevelStars()`，显示当前模式的星级和解锁状态
7. 修改设置面板中的记录显示，同时展示两种模式的星级并标注"常规"/"限时"
8. 修改成就检查中的星级统计，区分两种模式

**涉及文件**：`js/config.js`、`js/state.js`、`js/storage.js`、`js/game.js`、`js/settings.js`、`js/achievements.js`、`css/settings.css`

## 问题 5：关卡下拉框中两种模式的关卡混合展示

### 现象
点击关卡按钮后，常规模式和限时模式的关卡混在同一个列表中展示，没有区分。玩家无法直观看出哪些关卡是常规模式进度、哪些是限时模式进度。

### 原因
`updateDifficultyButtons()` 函数仅生成一个关卡列表，虽然已根据 `gameMode` 读取对应模式的星级和解锁状态，但两种模式没有在视觉上分离展示，且切换模式查看进度需要先切换游戏模式再打开下拉框。

### 解决方案
1. 在关卡下拉框顶部添加"常规"和"限时"两个标签页（tab），各显示对应模式的总星星数
2. 新增 `levelDropdownActiveTab` 变量跟踪当前查看的标签页
3. 点击标签页时刷新关卡列表，显示对应模式的星级和解锁状态
4. 跨模式选关时自动切换游戏模式（有未完成进度时需确认）
5. 打开下拉框时默认对齐当前游戏模式的标签页
6. 新增标签页相关 CSS 样式（含暗黑模式适配）

**涉及文件**：`js/game.js`（`updateDifficultyButtons`、`toggleLevelDropdown`）、`css/header.css`

## 问题 6：切换模式后当前关卡未重置，导致严重的逻辑错误

### 现象
常规模式通过第5关后到达第6关，此时切换到限时模式，游戏仍然停留在第6关，而限时模式可能仅解锁到第2关。玩家可以直接操作未解锁的限时模式关卡，严重违反游戏规则。

### 原因
`currentLevel` 是全局共享的单一变量，常规模式和限时模式共用。之前的修改实现了独立的解锁状态（`unlockedLevels` / `unlockedTimedLevels`）和独立的星级记录（`levelStars` / `timedLevelStars`），但**没有维护各自独立的当前关卡记录**。

切换模式时，`setGameMode()` 仅修改了 `gameMode` 并调用 `restartGame()`，但没有将 `currentLevel` 重置为新模式的实际进度，导致关卡号被"继承"到新模式中。

### 解决方案
1. 新增 `STORAGE_KEYS.normalCurrentLevel` 和 `STORAGE_KEYS.timedCurrentLevel` 存储键，分别保存两种模式的当前关卡
2. 新增 `saveCurrentLevelForMode(level, mode)` 函数，按模式分别持久化当前关卡号
3. 新增 `getFirstUnlockedLevel(unlockedObj)` 辅助函数，查找某模式下第一个已解锁的关卡
4. 修改 `loadGameData()`，初始化时根据当前模式加载对应的保存关卡，并校验该关卡是否已解锁
5. 修改 `setGameMode()`，切换模式时：
   - 先保存旧模式的当前关卡（`saveCurrentLevelForMode(currentLevel, oldMode)`）
   - 切换模式后，读取新模式的保存关卡作为 `currentLevel`
   - 校验目标关卡在新模式下是否已解锁，未解锁则回退到第一个已解锁关卡
6. 修改 `nextLevel()`、`changeLevel()` 和下拉框跨模式选关逻辑，关卡变化时同步调用 `saveCurrentLevelForMode()` 持久化

**涉及文件**：`js/config.js`、`js/storage.js`、`js/game.js`

## 问题 7：教程炸弹介绍卡片与教程指南卡片重叠遮挡

### 现象
在教程的炸弹介绍界面，`tutorial-bomb-modal`（炸弹介绍弹窗）与底部 `.tutorial-guide-content`（教程指南卡片）同时显示，产生视觉重叠遮挡，严重影响观感。

### 原因
教程进行到炸弹演示环节时，`bombExplode()` 函数显示炸弹弹窗（`tutorial-bomb-modal`），但没有隐藏底部的教程指南内容。由于 `.tutorial-guide-content` 的 `z-index: 1501` 高于 `.modal` 的 `z-index: 1000`，教程指南卡片会覆盖在炸弹弹窗上方，造成遮挡。

### 解决方案
1. 在 `bombExplode()` 函数中，显示炸弹弹窗时同步隐藏 `.tutorial-guide-content`（添加 `hidden` 类）
2. 在 `tutorialBombCloseBtn` 的点击处理函数和点击弹窗外部关闭的处理函数中，关闭弹窗时同步显示 `.tutorial-guide-content`（移除 `hidden` 类）
3. 在 `css/tutorial.css` 中添加 `.tutorial-guide-content.hidden { display: none; }` 样式规则

**涉及文件**：`js/game.js`、`js/events.js`、`css/tutorial.css`

## 问题 8：限时模式下启动教程，教程在限时模式中进行且计时开始

### 现象
如果在限时模式下点击"开始新手教程"，教程会在限时模式下进行，游戏倒计时会同时启动，不符合教程应在常规模式下进行的设计要求。

### 原因
`startTutorial()` 函数启动教程时，没有将游戏模式切换回常规模式，也没有停止倒计时，导致教程继承了当前的限时模式状态。

### 解决方案
在 `startTutorial()` 函数开头添加模式切换和计时器清理逻辑：
1. 将 `gameMode` 设为 `GAME_MODES.NORMAL`
2. 调用 `saveGameMode()` 持久化
3. 调用 `stopCountdown()` 停止倒计时
4. 调用 `updateModeButtons()` 更新UI按钮状态

同时在 `endTutorial()` 函数中添加相同的清理逻辑，确保教程结束后游戏回到常规模式。

**涉及文件**：`js/tutorial.js`

## 问题 9：教程缺少限时模式介绍

### 现象
教程步骤中只介绍了基本的翻牌配对、配对失败和炸弹机制，完全没有提及限时模式这一重要游戏特性，新手玩家无法从教程中了解到限时模式的存在和玩法。

### 原因
`tutorialSteps` 数组中没有限时模式相关的介绍步骤。

### 解决方案
在 `tutorialSteps` 数组中添加限时模式介绍步骤（位于炸弹演示之后、"开始游戏"之前），包含：
1. 限时模式规则文字说明
2. 交互式引导：高亮"限时"按钮，指引玩家点击切换模式
3. 交互式引导：切换到限时模式后，高亮卡片，指引玩家点击观察倒计时运行
4. 演示完成后自动切回常规模式

新增状态变量 `tutorialTimedModeActive`、`tutorialTimedCardClicked`、`tutorialTimedDemoTimer`，新增函数 `handleTutorialTimedModeClick()`、`handleTutorialTimedCardClick()`、`handleTutorialTimedNextClick()`、`completeTimedModeDemo()`、`clearTutorialTimedDemoTimer()`。

**涉及文件**：`js/tutorial.js`、`js/events.js`、`js/state.js`、`index.html`

## 问题 10：配对失败教程步骤存在明显停滞感

### 现象
教程进行到"配对失败会怎样"步骤时，展示配对失败结果后需要玩家手动点击"下一步"才能进入炸弹模块介绍，交互不够流畅，存在明显的停滞感。

### 原因
步骤5的 `action` 为 `show-mismatch-result`，只显示文字说明，没有自动前进机制，用户必须手动点击"下一步"按钮。

### 解决方案
在 `executeTutorialAction()` 函数中，为 `show-mismatch-result` 动作添加2.5秒的自动前进定时器：
- 进入该步骤时设置 `tutorialAutoAdvanceTimer`
- 2.5秒后自动前进到步骤6（炸弹介绍）
- 自动前进前检查当前仍在教程且仍处于该步骤
- 新增 `clearTutorialAutoAdvanceTimer()` 函数用于清理定时器
- 在 `updateTutorialStep()`、`startTutorial()`、`endTutorial()` 及所有重置函数中调用清理函数

**涉及文件**：`js/tutorial.js`、`js/state.js`

## 问题 11：限时模式教程步骤中卡片自动翻开（严重逻辑错误）

### 现象
教程进行到"限时模式体验（一）"步骤时，指引玩家点击限时模式按钮，但点击后棋盘上有一张牌被自动翻开，玩家还没有进行任何操作。同时教程卡在这一步，点击"下一步"按钮也没有任何反应。

### 原因
这是一个**事件冒泡 + 状态竞争**的严重逻辑bug，完整触发链如下：

1. 用户在步骤8点击「限时」按钮
2. `modeTimedBtn` 点击处理函数执行，调用 `handleTutorialTimedModeClick()`
3. `handleTutorialTimedModeClick()` 内部调用 `updateTutorialStep(9)`，此时 `currentTutorialStep` 已变为 9
4. **但点击事件还在继续向上冒泡**
5. 事件冒泡到 `document` 的全局点击处理器
6. 全局处理器读取 `step = tutorialSteps[currentTutorialStep]`，此时已经是步骤9（`wait-timed-card-click`）
7. 步骤9的 `showNext = true`，且 `action` 不是 `free-play`
8. 全局处理器检查点击目标是否在排除列表中——模式按钮（`.mode-btn`）**不在排除列表中**
9. 所有检查通过，自动执行 `tutorialNextBtn.click()`
10. 触发步骤9的下一步处理函数，调用 `autoFlipCard()` 自动翻牌

此外，即使卡片已翻转，`autoFlipCard()` 会因 `card.flipped` 检查提前返回，导致 `completeTimedModeDemo()` 永远不会被调用，教程卡住。

### 解决方案
采用**双重保险**机制彻底解决：

1. **修复1：在全局点击处理器中排除模式按钮**
   - 在 `document.addEventListener('click', ...)` 的教程处理逻辑中添加 `if (e.target.closest('.mode-btn')) return;`

2. **修复2：阻止模式按钮点击事件冒泡**
   - 在 `modeNormalBtn` 和 `modeTimedBtn` 的点击处理函数中添加 `e.stopPropagation()`，阻止事件冒泡到 `document`

3. **修复3：完整重置卡牌和游戏状态**
   - 在 `handleTutorialTimedModeClick()` 中添加完整的卡牌翻回和游戏状态重置逻辑，确保进入步骤9时所有卡片都是未翻转状态

4. **修复4：处理卡牌已翻转的边缘情况**
   - 新增 `handleTutorialTimedNextClick()` 函数，处理步骤9的"下一步"按钮点击，能正确处理卡牌已翻转的情况
   - 更新 `handleTutorialTimedCardClick()` 函数，当卡牌已翻转时直接启动游戏并调用 `completeTimedModeDemo()`

**涉及文件**：`js/events.js`、`js/tutorial.js`
